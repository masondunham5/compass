# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Compass is a local-first life planner (calendars, school, work, and training): FastAPI + SQLite backend, dependency-free HTML/CSS/JS PWA frontend, and an optional Garmin Connect Personal API sync.

## Commands

The virtualenv lives one level up, at `..\.venv` (the launchers check `.venv` first, then `..\.venv`).

```powershell
# Run the app (http://127.0.0.1:8765)
..\.venv\Scripts\python.exe -m uvicorn app:app --reload --port 8765

# Tests (all / single test)
..\.venv\Scripts\python.exe -m pytest
..\.venv\Scripts\python.exe -m pytest tests/test_app.py::test_garmin_csv_parser_keeps_runs_and_converts_kilometers

# Garmin sync (1–30 days); hits the real API using the key in .env
..\.venv\Scripts\python.exe garmin_sync.py --days 7

# Re-derive metric columns from stored raw responses (no API calls), e.g. after editing METRIC_FIELDS
..\.venv\Scripts\python.exe garmin_sync.py --rebuild

# Import past lifting sets from CSV (date,workout,exercise,set,weight_lbs,reps,rpe,notes); re-runnable, use --dry-run first
..\.venv\Scripts\python.exe scripts\import_lifting_history.py path\to\lifting_history.csv --dry-run

# Demo data (refuses to overwrite an existing DB) / DB backup into backups/
..\.venv\Scripts\python.exe scripts\load_demo_data.py
..\.venv\Scripts\python.exe scripts\backup_database.py
```

There is no linter or build step.

## Hands off

- `.env` holds the real `GARMIN_PERSONAL_API_KEY`. Do not read, edit, or print it.
- `Garmin API Key/` is private. Do not open or modify it.
- `data/compass.db` (renamed from `lifting_hub.db` automatically on first start) is the user's real health data. Tests must not touch it.

## Architecture

- **Modules** (backend logic is split by concern; `app.py` re-exports their names so `app.<name>` still works in scripts/tests):
  - `core.py` — paths (`DATABASE`, `DATA_DIR`, `BACKUP_DIR`), `.env` loading via `load_local_env()` at import (no python-dotenv; real env vars win), `connection()`, `initialize()` (schema), settings, `current_bodyweight()`, `auto_backup()`.
  - `exercises.py` — workout-line parsing, aliases, rest times, `estimate_1rm`, `progression_suggestion` (double progression; deload weeks suggest ~85%), `exercises_for`.
  - `planning.py` — `BlockDraftRequest`, routine templates, `phase_lines` (Build +1 set on first two lifts, Deload cap 2), `build_draft`, `retemplate_future_strength`.
  - `readiness.py` — `deterministic_training_recommendation` (documented in README; falls back to the previous night until today's Garmin sleep syncs; also HRV status, Body Battery at wake, sleep score, 3-day streak).
  - `activities.py` — CSV/TCX/GPX parsing and `match_garmin_activities` (same-day pass, then ±1-day pass for still-planned sessions).
  - `health.py` — training load (Garmin `activityTrainingLoad`, 7-day vs 4-week ratio), illness early warning (resting HR up + HRV down / breathing rate up on 2 of the last 3 days), sleep coach (debt vs Garmin sleep need, bedtime consistency, tonight's window from `next_bedtime_*`), long-term trends + Daniels VO₂-max race predictions, insights (lifestyle tags vs next-morning HRV/RHR/sleep score; lifting vs sleep), pain→exercise warnings and swaps, goals, habits (auto: sleep/steps/protein/check-in), and `ensure_health_schema` (body_measurements, pain_log, health_records, goals, habits, habit_checks; daily_health tags/protein/water). `health_api.py` holds its `/api/health/*` routes, including printable `report/monthly` and `report/doctor` HTML. Readiness takes illness and load spikes into account.
  - `assistant/` — the executive-assistant layer (time, not training); kept behind a small interface so it can become its own service later. `calendars.py`: read-only ICS feeds (links or uploaded files) parsed with `icalendar` + `recurring-ical-events`, expanded 14 days back / 180 ahead into `calendar_events`; the feed URL is a secret — stored only in the DB, exposed as `url_hint`, never in errors. Link feeds refresh every 3 h (lifespan background task). `availability.py`: busy minutes, free slots (6 AM–10 PM), best workout slot (prefers 3–8 PM), exam detection, `day_notes` for reschedule previews, `exam_alerts`. `routes.py`: `/api/assistant/*`. UI in `static/assistant.js` (Today's schedule card, Settings → Calendars).
  - `assistant/school.py` — **read-only** adapter for the separate School To Do app (`../school_todo`). Parses its `app.py` with `ast` and executes only the statements that build `ITEMS`/`ESTIMATE_MINUTES` in a sandbox (never runs the app), then applies `%LOCALAPPDATA%/School To Do` edits, hidden tasks, details (minutes, due time) and completions. Never writes there. Override paths with `SCHOOL_TODO_APP` / `SCHOOL_TODO_DATA` (tests do).
  - `assistant/work.py` — terms (school/break) and work shifts (weekly with `applies` school/break/always, or one-off dates).
  - `assistant/planner.py` — draft plan: fixed = calendar busy + work shifts + accepted blocks; places workouts (prefers 3–8 PM on their day), exam review (2×60 min before exams), then schoolwork by deadline in 30–90 min blocks from 9 AM, finishing a day early when possible, ≤240 min study/day, then to-dos (`kind "task"`, deadline first, ≤120 min/day). Accepted time anywhere counts toward a task; `cleanup` drops upcoming task blocks whose to-do was deleted or checked off. Overdue tasks aren't scheduled unless opted in (`/api/assistant/school/force`). Drafts are computed on the fly; `plan_blocks` stores accepted ones (treated as fixed). UI: `static/planner.js` (Week plan, School and Work screens).
  - `assistant/events.py` — your own events (`my_events`: one-off or repeating none/daily/weekdays/weekly/biweekly/monthly, `repeat_until`, `skip_dates`; edit/delete scope one/future/all, where "one" splits that date off) and to-dos (`todos`: minutes estimate, optional due date/time). `occurrences()` expands repeats into event-shaped dicts (`feed_kind "mine"`).
  - **Fixed time has one source:** `availability.fixed_events(db, day)` = ICS feeds + cached personal Outlook (`outlook_events`) + your events + work shifts. `day_summary` adds accepted plan blocks (`plan_items`); the planner uses `fixed_events` then accepted blocks. Add new busy sources there.
  - `GET /api/assistant/calendar?start&days` returns every item per day for the time grid (`source`: feed/outlook/mine/work/plan/draft/session; minutes within the day). Drafts come from `planner.build` for today onward; workouts without a placed block show as all-day chips. UI: `static/calendar.js` (Week tab Day/Week grids, item sheets, event/to-do forms, to-do list); `renderWeek` in `assistant.js` delegates to it unless the mode is List. `addDays` lives in `schedule.js`; all front-end scripts share one global scope, so never redeclare a top-level name.
  - `assistant/outlook.py` — link with the user's *personal* Outlook **main Calendar** via Microsoft Graph. **Writes:** accepted `plan_blocks` and occurrences of your own events (link id `mine:<event>:<date>`) (1 day back → 21 ahead) go to `/me/calendar/events`, tagged with the `Compass` category; `outlook_links` maps block → event with a fingerprint, so sync only creates/updates/deletes what changed and recreates events deleted in Outlook. `_move_to_main` is a one-time migration from the old separate "Compass" calendar (setting `outlook_target`). **Reads:** each sync caches the rest of the main Calendar (`/me/calendarView`, 60 days; skips linked ids and the Compass category) into `outlook_events` as busy time, with `organizer`/`series` flags. **Changing your own events:** only on explicit user action — `edit_event`/`delete_event` (`PATCH`/`DELETE /api/assistant/outlook/events/{id}`, one occurrence for a series) or accepting a planner `move` draft. `movable()` = timed, busy, you organize it, ≤4 h, not started. School calendars are ICS feeds and are never written. Sign-in is MSAL device-code (authority `consumers`, delegated `Calendars.ReadWrite` + `User.Read`) using the user's own Azure app registration (client ID in `settings.outlook_client_id`); the token cache lives in `data/outlook_token.bin`, encrypted with Windows DPAPI. Triggers: plan accept/unaccept and schedule apply/undo (`sync_soon`, debounced, no-op when not connected) plus the 30-min background loop. Errors must never include the token. Tests use a fake Graph transport (`tests/test_outlook.py`; `default_calendar` = the user's own events).
  - **Check-in (done / missed):** `plan_blocks.outcome` is `''`, `done` or `missed` (`outcome_at`). `planner.mark` only accepts blocks that have started; marking missed rebuilds the plan and auto-accepts replacement blocks for the same kind+ref (up to the missed minutes), returning a message. Missed blocks keep their slot busy in the planner but don't count as work done (planner, `plan_items`, `events.open_todos`, the School planned minutes), and are deleted from Outlook; done blocks get a "✓ " subject prefix. Unmarked past blocks count as done. `planner.checkin` lists unmarked blocks that ended in the last 3 days. API: `POST /plan/blocks/{id}/outcome`, `GET /plan/checkin`. UI: `renderCheckin` in `calendar.js` (Today `#checkin-today`, Week `#checkin-week`) plus Done/Missed buttons in the plan-block sheet.
  - **Planner moves:** movable Outlook events sit in `Day.held` (busy, but liftable). Only when schoolwork or a dated to-do still can't fit before its deadline, `relieve` → `_make_room` frees a slot by suggesting a `move` draft (kind `move`, `ref` = Outlook event id, `from_date/from_start/from_end`, `for_title`), at most `max_moves` per draft, placed at the time nearest the original (`_closest`). `/plan/accept` applies move drafts with `outlook.edit_event`; ignoring them changes nothing.
  - `assistant/schedule.py` — rescheduling: move one session, skip (to tomorrow, or push everything after it), push the plan back N days, or swap two sessions' days (`swap_sessions`, optionally the next N pairs of the same two workout types — `workout_type` drops the `W5 ·` tag and `· Volume` variant; each pair is all-or-nothing; options from `/api/schedule/swap-options/{id}`). Never moves completed/cancelled/locked/logged sessions or race day; race-plan runs never cross race day. `/api/schedule/preview` and `/apply` take the same request; the last change is stored for one-step `/api/schedule/undo`. UI in `static/schedule.js`.
  - **Places & travel:** `assistant/places.py` (`places`, `travel_times` tables). Event locations match a place by keyword / name / street (`resolve`; online → `"virtual"`, unknown → no travel; work shifts use the Work place via `place_hint`). `day_travel` gives travel strips (Home → … → Home) and "too far apart" warnings; a user event titled "Drive/Commute/Bus… " counts as that travel. The planner adds strips to busy time and pads strength workouts when `lift_place` isn't Home (`workout_padding`). `estimate` geocodes with Nominatim and routes with routing.openstreetmap.de (only on request; manual minutes never overwritten). Calendar items get `place`, `directions`, and `source: "travel"` strips. UI: `static/places.js` (Settings → Places & travel).
  - **All-day events:** a *busy* all-day event blocks the whole planning day in `_busy_blocks`; free ones are labels. `day_overrides` (keyed by `allday_key` = kind|title|date) lets you block a day even on read-only calendars (`POST /api/assistant/allday`).
  - **Chat assistant:** `assistant/chat.py` (+ `/api/chat` router) and `static/chat.js` (floating button, sheet, voice via the browser's SpeechRecognition; replies to spoken messages are read aloud). `commands.py` handles built-in commands first (swap/move/push workouts, add to-do) with no AI. Otherwise an OpenAI-compatible provider is called — Groq (`gsk_`), xAI (`xai-`) or Gemini (`AIza`), chosen by key prefix; the model is picked from the provider's `/models` list (`pick_model`). The key lives in `data/chat_key.bin` (DPAPI, via `outlook._dpapi`), never in `.env`. The model gets a compact schedule (`schedule_text`: workouts by id, your events `m:<id>:<date>`, personal Outlook `o:<hash>`, plan blocks `b:<hash>`, school/work marked read-only) and tools; action tools only create **proposals** (`propose` validates and previews with the app's own functions, stored in memory for an hour). `apply` runs a proposal on Confirm and returns an undo proposal. Tests use a fake provider transport (`tests/test_chat.py`).
  - **Layout:** phones get the bottom tab bar and one column. At ≥1100px the tab bar becomes a left rail, Today splits into schedule | training (`.today-main` / `.today-side`) and Week into calendar | check-in, plan and to-dos (`.week-main` / `.week-side`, sticky). On phones those wrappers are `display: contents` and CSS `order` keeps the check-in and plan above the calendar. Other views stay a centered 860px column.
  - `app.py` — FastAPI app (lifespan runs `initialize()` + `auto_backup()`), request models, and every `/api/*` route; serves `static/`.
- **Tests must patch `core.DATABASE`, `core.DATA_DIR`, `core.LEGACY_FILE` and `core.BACKUP_DIR`** (see fixtures). `tests/test_api.py` exercises routes through `TestClient`.
- **Schema** is created in `core.initialize()` with `CREATE TABLE IF NOT EXISTS` (it also calls `garmin_sync.ensure_schema`, so Garmin columns exist before the first sync); there is no migration framework, so new columns on existing tables need an explicit `ALTER TABLE ... ADD COLUMN` guarded by a `PRAGMA table_info` check. `connection()` returns a new `sqlite3` connection; `with connection() as db:` commits on exit but does not close.
- **Backups:** `auto_backup()` snapshots to `backups/auto_compass_*.db` at most once per ~20 h (on startup and before each Garmin sync) and keeps the newest 14; manual `scripts/backup_database.py` backups are never pruned.
- **`garmin_sync.py`** imports from `core` and `activities`. `run_sync(days)` exchanges the API key for a bearer token, pulls the activity list, then per day (newest first) calls four endpoints (`DAILY_ENDPOINTS`: summary, sleep, HRV, heart rate) and commits that day immediately. Each run writes a row to `garmin_sync_log` (`running` → `success` / `partial` / `error`), which the UI reads for status/history.
  - **Rate limiting:** all HTTP goes through `_request`, which paces calls (`GARMIN_REQUEST_INTERVAL`, default 1.5 s, doubled after a 429) and retries 429/5xx/network errors with exponential backoff honoring `Retry-After` (`GARMIN_MAX_RETRIES`, default 5).
  - **Errors:** `GarminFatalError` (bad key, persistent 429, no network) stops the sync; days already saved are kept and the run returns `status: "partial"`. `GarminEndpointError` (other 4xx/5xx) skips just that endpoint for that day. 404/204 mean "no data".
  - **Storage:** the full response of every endpoint is kept in `garmin_raw_responses (calendar_date, endpoint)`; raw activity JSON goes in `imported_activities.raw_json`. Useful fields are copied into `garmin_daily_metrics` columns defined by `METRIC_FIELDS` (column, type, endpoint, keys). Add a field there and `ensure_schema()` adds the column on the next sync. Dotted keys are exact paths; plain keys are searched recursively. Upserts use `COALESCE`, so a null never overwrites a stored value.
- **Garmin ↔ plan matching:** after saving activities, `run_sync` calls `app.match_garmin_activities`, which links each unlinked Garmin activity to the same-day session of the same kind (strength ↔ "Strength Training", run ↔ any running type). A planned session becomes completed with a Garmin-sourced `logs` row; an already-completed one is only linked. History hides linked activities and shows their duration/HR on the session row.
- **VO₂ max** is not in Garmin's activity list; `sync_vo2_max` makes one request to `/metrics-service/metrics/maxmet/daily/{start}/{end}` (last 30 days) and fills `garmin_daily_metrics.vo2_max`.
- **Triggers for sync:** `POST /api/garmin/sync` (first run backfills 14 days, then `GARMIN_SYNC_DAYS` capped at 7), `POST /api/garmin/backfill` (30 days), the CLI, and the daily Task Scheduler job from `scripts/register_garmin_sync_task.ps1`.
- **`GarminSyncError`** messages are shown to the user and must never include the key or token.
- **Consumers of Garmin data:** `/api/garmin/dashboard` and `/api/recommendations/training` read `garmin_daily_metrics` (the rules engine uses `sleep_seconds`, `hrv_ms`, `resting_hr`, `stress_avg` with a 28-day rolling baseline). Keep those column names stable.
- **Product shape:** Compass is a life planner; health/training is one section. Tabs: **Today** (greeting, alerts, Today's schedule from calendars, the training card, habits, recovery snapshot) · **Week** (`renderWeek` in `assistant.js`: busy hours, exams, workouts, best slot per day; tap a day for its agenda) · **Health** (Train / Recovery / Progress as sub-tabs injected by `app.js`; `selectView("health")` reopens the last one) · **More** (calendars/settings, records, reports). `TAB_FOR_VIEW` maps every view to its tab. The project folder (`ai-assistant\compass`), launchers (`Launch Compass.cmd`) and database (`data/compass.db`) are all named Compass.
- **`static/health.js`** renders the health features (Today alerts/habits, Recovery load/sleep/body/pain, Progress goals/insights/trends, Records view, reminders) using `app.js` globals; `app.js` calls `window.renderHealthHub()` after each `load()`. Reminders use the Notification API while the app is open (no server push yet).
- **Frontend** (`static/app.js`, `index.html`, `styles.css`) is plain JS calling the JSON API; no build tooling. It is a phone-first dark UI with the four tabs above plus Workout and Settings views; desktop shows the same column centered at 640px. Today renders entirely from `GET /api/today` (week strip, focus session with short-day set caps, readiness headline, latest Garmin night, up next). Recovery reads the latest night from that same payload and trends from `/api/garmin/dashboard`. Colors are CSS custom properties at the top of `styles.css`. Bump the `?v=` query on the CSS/JS links in `index.html` (and `CACHE` in `service-worker.js`) when shipping UI changes.
- **Workout templates:** the default split `logged-routine` (`ROUTINE_DAYS` / `ROUTINE_BY_DAYS` in `app.py`) mirrors the lifting log; deload weeks cap every exercise at 2 sets. `EXERCISE_ALIASES` maps alternate names to the logged name, and `normalize_exercise` uses it, so progress and last-weight suggestions merge aliases.
- **Workout lines** are `"Name — sets × reps"` with an optional `" @ 135 lb"` target. Set logs reference exercises by **index** into `workout_json`, so the add/swap/edit/remove endpoints (`/api/sessions/{id}/exercises…`) keep indices aligned; removing an exercise re-indexes later logged sets.
- **`catalog.py`**: static exercise list + `RUN_TYPES` (easy, tempo, intervals, long, …) and `PACE_FACTORS` relative to marathon pace. `/api/exercises/catalog` merges the list with every logged exercise and ranks by usage.
- **`race_plan.py`** (pure, unit-tested): `generate_plan()` builds Base → Build → Peak → Taper → Race week from race date, distance, current weekly miles and run days; ≤~12% weekly growth, cutback every 4th week, long-run ramp to the distance cap (20 mi marathon). Races live in the `races` table; `POST /api/races/{id}/apply` writes runs as sessions (`source = race:<id>`) and replaces planned, unlocked block runs from the plan's first week through race day. Block activation/revision skip run days covered by an applied race.
- **Click-testing:** run the app against a copy of the DB (set `core.DATABASE`, `core.DATA_DIR`, `core.BACKUP_DIR` before importing `app` and calling `uvicorn.run`) so test edits never touch real data.
- **Races** also expose planned-vs-actual weekly miles (Garmin) and `POST /api/races/{id}/recalibrate`, which rebuilds remaining weeks from the last two weeks' actual mileage.
- **Weekly review:** `GET /api/review/week?offset=0|-1|…` (sets by muscle group via `catalog.EXERCISES`, records, running vs plan, recovery vs prior week). Bodyweight lifts (`BODYWEIGHT_EXERCISES`) add bodyweight from the latest check-in or the `settings` table to their 1RM.
- **Short-day rule:** when readiness is 51–75 on a strength day, the engine keeps every exercise but caps each at 2 sets (`adjusted_sets`) and ~60% of the time (`adjusted_minutes`); the Today card offers "Do the full N min instead".
- Activities imported from Garmin are only linked to a planned session after an explicit user action (`/api/activities/{id}/link`); recommendations never modify the schedule.
